### Detalles de contrato que condicionaron el cliente

1. **Envelope**: éxito **crudo** (`res.json(result.data)`), error con envelope
   `{ success:false, error:{ code, message, statusCode } }` → se usa `*Raw`.
2. **Paginación**: solo `expenses` y `savings-goals` listan con página (`{ items,
   total, page, limit }`). **`calendar-events` devuelve un array plano** (sin
   paginación) — el cliente no asume envelope.
3. **Savings — rutas de tablero sin prefijo de scope**: `/savings-goals/:goalId/
   {cells,movements,contributions}` cuelgan del goal (la autorización se resuelve
   desde el goal, mismo criterio que los movimientos de inventory). Los endpoints de
   meta sí van bajo scope (`/users/...`, `/households/:id/...`).
4. **`mark`/`unmark` son `PATCH`** (no POST) y devuelven `IMarkCellResultDTO`
   (`{ movement, cell, goal, statusChanged, previousStatus, newStatus }`).
5. **Savings no tiene endpoint de update de meta** (solo create/get/delete). El
   cliente no lo inventa.
6. **Calendar: `scope` y `householdId` NO viajan en el body** — se derivan de la
   ruta. `CreateCalendarEventSchema` usa `additionalProperties: false`, así que
   enviarlos daría 400. El `ICreateCalendarEventInput` de la interfaz de APP los
   declara, pero el validator los rechaza; el móvil **no** los envía (verificado con
   un test que inspecciona el body serializado).
7. **Calendar update acepta `endAt: null`** para limpiar la hora de fin
   (`Type.Union([String, Null])`); el mapper distingue "omitido" de `null`.
8. **Decimales como string**: `amount`, `targetAmount`, `savedAmount`, `denomination`,
   `balanceAfter`, `totalPaid`, `remainingAmount` se mantienen como `string` (no
   `number`) para no perder precisión.
